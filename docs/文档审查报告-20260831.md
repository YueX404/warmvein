# 项目文档对齐性审查报告

> 审查日期：2026-08-31
> 审查范围：README.md、CHANGELOG.md、CLAUDE.md、docs/ 全部 12 份文档、config/ SQL 脚本、docker/ 两份 compose、.env.example，并与 src/ 实际代码、根目录《需求列表 v20260827.md》源需求交叉核对。

---

## 一、总体结论

文档体系**分层结构良好**（需求→设计→功能→任务→计划→API→数据字典→部署），版本号统一为 v2026.08.31，17 个 API 端点、错误码、里程碑 M1-M4 在各文档间基本一致，数据字典与 `heat_init.sql` 高度对应。

但存在 **4 个 P0 级问题**：①文档把"规划"写成了"现状"，与实际代码严重脱节；②项目内并存两套互相矛盾的开发分工方案；③API 前缀契约冲突；④MySQL 库名/账号三处不一致（会直接导致部署失败）。**当前文档状态不适合直接交给两位开发人员照此开工，需先修复 P0。**

## 二、P0 — 阻断级问题（不修复会导致开发/部署失败）

### P0-1 规划写成现状，文档与代码严重脱节

README「项目结构」和 CLAUDE.md「目录结构」中列出的以下文件**全部不存在**：

| 文档声称 | 实际 |
|---|---|
| `heat_generate_logs.py` / `heat_kafka_producer.py` / `heat_spark_analysis.py` / `heat_train_model.py` | 不存在（仅有旧工业模板 `generate_logs.py` 等 4 个） |
| `routes_heat.py` 等 7 个 `routes_*.py` | 不存在 |
| `algorithm/`、`services/`、`consumers/`、`config/settings.py`、`db.py`、`kafka_topics.py`、`response.py` | 全部不存在 |
| `web/` 前端工程 | 整个目录不存在 |
| `config/logstash/heat_kafka_to_es.conf` | 不存在（仅有旧 `kafka_to_es.conf`） |
| CLAUDE.md 称「main.py F0 已锁定，含 7 路由挂载」 | main.py 仍是**智能制造工业设备监控平台**（标题、设备列表 CNC/RBT/INJ 全是工业设备，无任何 include_router） |

CLAUDE.md 自相矛盾：前文写「设计文档与实现计划已生成，**待开发启动**」，后文目录结构却按已完成状态罗列。README「快速开始」第 2~5 步命令（`heat_generate_logs.py` 等）**现在执行全部会失败**。

**建议**：README/CLAUDE.md 的目录结构与快速开始章节明确标注「规划态（F0/Dev 计划实施后生效）」，或直接注明以 `docs/superpowers/plans/` 为准；CLAUDE.md 删除「F0 已锁定」表述或改为「F0 计划已评审、待实施」。

### P0-2 两套互相矛盾的开发分工方案并存

- **方案一**（README「开发团队分工」、CLAUDE.md、F0/Dev-1/Dev-2 三份 plan）：Dev-1/Dev-2 **模块垂直拆分**，各自前后端全包。README 明确写「采用模块垂直拆分（**非前后端拆分**）」。
- **方案二**（`docs/开发任务拆分-角色A-平台与智能底座.md`、`角色B-前端与展现层.md`）：角色 A=**全部后端**、角色 B=**全部前端**的前后端拆分，与方案一直接冲突。

更严重的是 **README 文档索引与 CHANGELOG 都把「角色 A/B」文档错误描述为 Dev-1/Dev-2 的任务**（如「开发任务-运行流：Dev-1 负责 1.2/2.2/8.x…」），但文件实际内容是前后端拆分——**索引描述与文件内容完全不符**，新加入的开发者会被直接误导。

从时间戳看（角色 A/B 文档 15:27-16:04，F0/Dev 计划 16:13-16:23），角色 A/B 是被垂直拆分方案**取代的旧方案残留**。

**建议**：二选一。若采用 Dev-1/Dev-2 方案：更新角色 A/B 两份文档为废弃状态（或改写为 Dev-1/Dev-2 内容），同步修正 README 索引与 CHANGELOG 的描述。

### P0-3 API 路径前缀契约冲突（号称"唯一冻结契约"却自相矛盾）

- F0 计划、Dev-1/Dev-2 计划、README 技术架构、CLAUDE.md 均说：**`/api` 前缀**（F0：「main.py 已锁定挂载 7 路由，`/api` 前缀」；Dev-1 公众服务调 `POST /api/sms/send`）。
- 但被任务拆分文档指定为「**唯一冻结契约**」的《功能开发文档》§3 与《api-guide.md》全部 17 个端点**均无 `/api` 前缀**（`/heat/stations`、`/sms/send`…）。

前端 Mock 按无前缀契约写、后端按 F0 的 `/api` 前缀实现，联调时必炸。

**建议**：立即统一（推荐全局加 `/api` 前缀，与 F0 一致），同步修订功能开发文档 §3、api-guide.md 全部端点及系统设计文档 §8。

### P0-4 MySQL 库名/账号三处不一致（部署必失败）

| 出处 | 库名 | 账号 |
|---|---|---|
| `config/mysql/heat_init.sql`（实际会执行） | **warmvein** | 无（root 执行） |
| `.env.example` / deployment.md §4.2 / 数据字典 | **warmvein** | warmvein |
| `docker-compose-vm.yml`（`MYSQL_DATABASE: heat_platform`，挂载 `../config/mysql:/docker-entrypoint-initdb.d`） | **heat_platform** | heat/heat123 |
| 部署文档-虚拟机部署.md §7.1「应看到 heat_platform 数据库」 | **heat_platform** | — |

按 VM 文档实际部署后：MySQL 会同时创建 `heat_platform`（空库）和 `warmvein`（SQL 内 `CREATE DATABASE warmvein` + 建全部 16 张表）；`heat` 用户默认权限在 `heat_platform` 上，**连接后看不到任何业务表**——文档承诺的「应看到 md_station, md_user, biz_alarm 等表」不会发生。

**建议**：统一为 `warmvein`（与 SQL、.env、数据字典多数一致）；修改 vm compose 的 `MYSQL_DATABASE/MYSQL_USER`，修正 VM 部署文档 §7.1。

## 三、P1 — 重要问题（对齐性缺陷，应尽快修复）

1. **系统设计文档 §2.1 架构图 Kafka Topic 写成旧模板名** `device-sensor-topic / device-alarm-topic`，与全项目 `heat-sensor-topic / heat-alarm-topic`（README、功能开发文档、数据字典、.env、F0）冲突。属改造遗留笔误。

2. **公众服务（11.2）无 API 端点，路由挂载关系存在缝隙**：
   - README/CLAUDE/F0 均列 `routes_public.py`（7 模块之一，Dev-1 负责 11.2），但 17 端点契约中**没有任何 `/public/*` 端点**；需求 FR-11.9.2「线上报修与进度查询」也未映射到任何接口（隐含复用 `/workorder/create`？该接口归 Dev-2，归属未说明）。
   - 契约中 `/console/climate-compensate`、`/patrol/plan/generate`、`/forecast/list` 三个前缀不在 7 模块（heat/alarm/workorder/plan/sms/twin/public）之列，应挂在哪个 routes 文件、归 Dev-1 还是 Dev-2 **未定义**——双人并行开发时这三处会互相踩脚或无人认领。

3. **Kafka Topic 清单不一致**：F0 定义 4 个 topic（另含 `heat-forecast-topic`、`sms-notify-topic`），数据字典 §5 和 `.env.example` 只登记 2 个，Dev-2 计划明确依赖 `SMS_NOTIFY_TOPIC`。

4. **CHANGELOG 两处失实**：
   - 「heat_init.sql（14 张表）」——实际 **16 张**（6 主数据 + 10 业务，数据字典与 SQL 均为 16）。
   - 未记录 8-31 晚新增的 `docker/docker-compose-vm.yml` 与 `docs/部署文档-虚拟机部署.md`（17:42/17:44，晚于 CHANGELOG 最后更新 17:35）。

5. **两份部署文档未衔接，README 索引缺失**：
   - README 文档索引只列 `deployment.md`，未列《部署文档-虚拟机部署.md》。
   - deployment.md 称「当前 docker-compose.yml 未包含 MySQL 容器，需额外配置或使用外部 MySQL」，与 README 技术栈表「MySQL 8 / Redis 7」的阅读预期冲突；VM 版 compose 已加 MySQL/Redis，两份部署文档互不引用，开发者无从知道该用哪份。
   - VM 部署文档 §7.3「创建供热数仓表」给出的命令实际是跑 Spark 分析和建库，**并未执行 `heat_ddl.sql`**（执行方式只在 deployment.md §4.1），且引用了尚不存在的 `heat_spark_analysis.py`。

6. **需求分析文档「完整」措辞与裁剪事实矛盾**：§3.1 称数字孪生（10.1+10.2）「完整」、能效（8.1+8.3）「完整」，但括号内实际只覆盖「热力场仿真+停暖恢复仿真」「气候补偿节能+能效对标」——源需求 10.1 的实景融合/模型轻量化、10.2 的水力/燃气/水质仿真、8.2 碳足迹等均未纳入。括号有交代，但「完整」二字会在验收时引起争议，建议改为「核心能力」或「按括号范围」。
